# Создание карточки товара (измерительного прибора) с помощью LLM

Сервис принимает на вход структурированное описание измерительного прибора и возвращает черновик карточки товара: SEO-заголовок, SEO-описание, таблицу ключевых характеристик, несколько запросов для SEO-оптимизации страницы товара и блок его описания простым текстом (какие задачи решает и для кого подходит).

## Инструкция по установке и запуску
Понадобится:
- Python (проверено на версии 3.14.9, вероятнее всего, будет работать и на более ранних или поздних)
- Менеджер пакетов [uv](https://github.com/astral-sh/uv)
- [Ollama](https://ollama.com) (локально или на сервере)

Для запуска:
- Склонируйте этот репозиторий:
```bash
git clone https://github.com/trolley813/meters-llm.git
```
- Установите зависимости Python:
```bash
uv sync
```
- При необходимости, измените значения переменных окружения в `.env`:
    - `OLLAMA_HOST`: адрес сервера Ollama (по умолчанию - локально)
    - `OLLAMA_MODEL`: используемая модель (по умолчанию - Qwen 3.8)

- Запустите проект:
```bash
uv run meters-llm
```

- Приложение будет доступно по адресу http://127.0.0.1:7860 (интерфейс на Gradio и API).

## Отправка данных

### Через UI (предпочтительно)

1. Заполните форму в левой части страницы: название прибора, производитель, характеристики (формат см. ниже) и 
2. Нажмите кнопку "Сгенерировать".
3. Подождите результата (до нескольких минут, в зависимости от модели и аппаратного обеспечения).
4. Результат отобразится в правой части страницы. Можно просмотреть его в отформатированном виде и скопировать в формате Markdown для дальнейшего редактирования и обработки.

#### Формат ввода характеристик:
```json
{
    "Характеристика 1": "Значение 1",
    "Характеристика 2": "Значение 2",
    "Характеристика 3": "Значение 3"
}
```

Также можно воспользоваться несколькими готовыми примерами (таблица слева внизу, форма заполняется данными, если щелкнуть по нужной строке таблицы).

### Через API (для автоматизированной обработки)

1. Отправьте POST-запрос:

`POST /gradio_api/call/v2/generate-card`

Формат запроса:

```json
{
    "name": "Название прибора",
    "manufacturer": "Производитель",
    "specs": {
        "Характеристика 1": "Значение 1",
        "Характеристика 2": "Значение 2",
        "Характеристика 3": "Значение 3"
    },
    "description": "Описание"
}
```

Формат ответа:
```json
{
    "event_id": "0123456789abcdeffedcba9876543210"
}
```

**Обратите внимание**: ответ возвращается сразу и выдает "ручку" (`event_id`), по которой можно отслеживать выполнение запроса.

2. Для получения текста отправьте GET-запрос:

`GET /gradio_api/call/v2/generate-card/<event-id>`

Здесь `<event-id>` - значение, полученное на 1-м шаге. Например, `/gradio_api/call/v2/generate-card/0123456789abcdeffedcba9876543210`

Запрос будет выполняться в потоковом режиме (streaming), когда все будет готово, вернет текст в формате Markdown.

## Использованные решения и их обоснование (что, как, почему)

### Что использовано?

Язык Python, официальная библиотека Ollama для отправки запросов в LLM, фреймворк Gradio для построения UI и API.

### Почему UI и Gradio в первую очередь?
Из технического задания ясно, что основные пользователи сервиса - менеджеры, отвечающие за наполнение сайта/базы карточками товаров. Они могут совсем не знать про такие вещи, как JSON, API и т.п. Поэтому ставилась цель сделать сервис максимально простым для непрограммиста (хотя, увы, полностью исключить JSON-синтаксис не удалось - см. ниже в разделе "Что можно улучшить").

### Почему именно Ollama, а не Anthropic/OpenAI/GigaChat и т.п.?

Для данной конкретной задачи, локальные модели имеют несколько преимуществ:
- независимость от внешних сервисов (могут быть недоступны/заблокированы для пользователей из России, да и банально может пропасть соединение с Интернетом)
- экономичность (не нужно платить за токены)
- возможность выполнения на пользовательском оборудовании (уже модели с 27 млрд параметров и менее решают задачу достаточно эффективно и корректно, при этом могут работать на обычном ПК, пусть и довольно мощном)
- отсутствие утечек данных (могут быть приборы с частично закрытыми характеристиками (секретность, военное исполнение и т.п.), передача которых на сервера, тем более зарубежные, крайне нежелательна)

P.S. Ollama поддерживает и нелокальные облачные модели, если такая необходимость все же возникнет. Переписывать код сервиса для этого не нужно.

### Почему официальная библиотека Ollama?

В данном случае она достаточно просто решает поставленную задачу (работа с API), надстройки вроде LlamaIndex уже излишни. *Keep it simple stupid* (с англ. - делай просто и понятно).

### Почему такой системный промт? Почему модель Qwen 3.8?

Системный промт (константа `SYSTEM_PROMPT` в коде):
```
Вы - ассистент контент-менеджера. Ваша задача - сформировать в формате Markdown карточку товара измерительного прибора. Она должна содержать: SEO-заголовок до 70 символов, SEO-описание на 800-1200 символов, список ключевых характеристик, 3-5 запросов для оптимизации веб-страницы карточки и блок для менеджера - кому подходит данный прибор и какие задачи решает. Входные данные подаются в виде JSON-объекта: ключ name - название, manufacturer - производитель, specs - технические характеристики в виде словаря, description - описание. Очень важно - не используйте характеристики, которых нет во входных данных, если какое-либо поле отсутствует, поставьте пометку "нет данных". Также не используйте данные, которые заведомо некорректны.
```

Практика показала, что при использовании данного промта в качестве системного сервис решает все возложенные задачи:
- выводит карточку товара в полном соответствии с указанным форматом;
- использует только характеристики из запроса (не выдумывает то, чего там нет, в случае отсутствия данных ставит соответствующую метку и предупреждает об этом);
- корректно интерпретирует опечатки в тексте (например, диапазон частот "10-106 Гц" был верно интерпретирован как от 10 до 10<sup>6</sup> Гц, т.е. до 1 МГц);
- предупреждает о противоречиях (например, разные характеристики в названии и описании);
- пишет корректные на вид и правдоподобные SEO-запросы (замечание: автор не занимался SEO-оптимизацией);
- выдает данные в формате, удобном для менеджера.

Модель Qwen3.8-27B была использована после практического тестирования как дающая лучшие результаты (лучше всех понимает русский язык, выдает наиболее соответствующие форме результаты и не пытается исправить то, что не нужно исправлять). Меньшие по размерам модели семейства Qwen (например, Qwen3-vl-8B) могут быть использованы при недостатке ресурсов, их вывод лишь незначительно хуже.


### Почему такие лимиты на токены?
Установленные лимиты на вход и выход (16384 токена) позволяют уместить всю необходимую информацию: на входе - системный промт и данные в JSON, на выходе - полная карточка товара (часть лимита тратится на "раздумья" (thinking) модели). При меньшем лимите есть риск неполноты данных (при 8192 может обрезаться выходной текст - в примерах выше количество использованных выходных токенов доходило до примерно 8400), при большем - сильное замедление работы модели.

## Что можно улучшить? Какие есть ограничения?

- Сейчас по API содержимое выдается дважды; это происходит из-за ограничений Gradio, поскольку контент выдается и для просмотра, и для копирования. Возможно, стоит вынести генерацию в отдельную функцию и использовать ее раздельно для UI и API.
- Протестировать другие модели (локальные и облачные), возможно, потребуется донастройка промта.
- Сделать JSON-ввод характеристик прибора более удобным для непрограммистов (например, в чисто текстовом виде через двоеточие).
- Иногда модель выдает в явном виде количество символов в полях, для которых задано ограничение (видно в примерах). Менеджер должен обращать на это внимание перед копированием. С другой стороны, это можно считать и преимуществом - гарантией того, что лимиты соблюдены.
